# Moodle .mbz backup format reference (Moodle 4.1, backup_version 2022112800)

Read this to understand, debug, or extend the format. Verified against a real
Moodle 4.1 backup and the `MOODLE_401_STABLE` source.

## Contents

## 1. Archive layout & what's required

A `.mbz` is a **gzip-compressed tar** (`.tar.gz`). Extract with `tar -xzf x.mbz`.

```
.ARCHIVE_INDEX             generated by Moodle's packer; NOT required for restore
moodle_backup.xml          REQUIRED — the roadmap of the whole backup
files.xml                  REQUIRED — central file store (may be empty <files></files>)
course/
  course.xml               course definition
  enrolments.xml roles.xml filters.xml calendar.xml inforef.xml
  completiondefaults.xml contentbank.xml
sections/
  section_<id>/section.xml + inforef.xml
activities/
  <modname>_<cmid>/<modname>.xml    type-specific main file
                    module.xml inforef.xml roles.xml grades.xml
                    grade_history.xml calendar.xml filters.xml [grading.xml]
files/<xx>/<contenthash>   physical file contents (only if attachments)
questions.xml groups.xml scales.xml outcomes.xml roles.xml completion.xml
moodle_backup.log          (can be empty)
```

**Required vs optional for restore:** `moodle_backup.xml` and `files.xml` are
mandatory. Per activity, `<modname>.xml`, `module.xml`, `inforef.xml` are
required; `roles.xml`/`grades.xml`/`grade_history.xml` are practically always
present and read (empty shells are fine). Top-level stores
(`scales.xml`, `outcomes.xml`, `groups.xml`, `completion.xml`, …) and the
`questions.xml` file are read when present; restore tolerates their absence but
this generator always writes them as empty shells for safety.

**`.ARCHIVE_INDEX` format** (TAB-separated), first line is a header:
```
Moodle archive file index. Count: <N>
<path>          d   0      ?          (directory; mtime is literal "?")
<path>          f   <size> <mtime>    (file)
```
The index lists entries in the same order they appear in the tar, and does not
list itself. Restore reads tar headers directly, so a missing/imperfect index
does not break a full restore.

## 2. ID cross-reference network

Several **independent** id spaces must stay internally consistent:

- **course**: `course.xml@id` = `moodle_backup.xml/original_course_id`;
  `course.xml@contextid` = `original_course_contextid`.
- **section**: `section.xml@id` = folder suffix `section_<id>` =
  `moodle_backup.xml/.../section/sectionid` + `directory`.
- **activity (three distinct ids!)**:
  - **cmid** (course-module id): folder suffix `<mod>_<cmid>`, `module.xml@id`,
    `<activity moduleid>`, `moodle_backup.xml/.../activity/moduleid`, and each
    entry of a section's `sequence`.
  - **instance id**: `<activity id>` and `<modname id>` (the module's row id).
  - **module contextid**: `<activity contextid>`; used by `files.xml` records and
    the module's `roles.xml`.
- **role**: `roles.xml/role@id` ↔ `enrolments.xml/roleid` ↔
  `course/inforef.xml/roleref`.
- **question**: `questions.xml/question_category@id` ↔
  `inforef.xml/question_categoryref`; quiz slots →
  `question_reference/questionbankentryid` ↔ `question_bank_entry@id`.
- **file**: `files.xml/file@id` ↔ `inforef.xml/fileref/file/id`; `contenthash`
  ↔ physical path `files/<contenthash[:2]>/<contenthash>`.

**Invariant:** every cmid in a section's `sequence` must have a matching
`<activity>` in `moodle_backup.xml` and an `activities/<mod>_<cmid>/` folder.
The generator guarantees this by building `sequence` from the included
activities.

## 3. `$@NULL@$` and escaping rules

- `$@NULL@$` encodes SQL **NULL**. It is distinct from an empty string
  (`<x></x>` = `""`) and from `0`. Use the right one — Moodle restores them
  differently.
- Text/HTML content is **HTML-entity-escaped** directly in the text node
  (`&lt;p&gt;…`), not wrapped in CDATA. `&` → `&amp;` everywhere, including
  inside `availabilityjson` (`{"op":"&amp;",...}`).
- Serialized PHP arrays appear verbatim in some fields (`displayoptions`,
  `parameters`), e.g. `a:1:{s:10:"printintro";i:1;}` / `a:0:{}`.
- Timestamps are Unix epoch seconds.
- Every file starts with `<?xml version="1.0" encoding="UTF-8"?>` and no leading
  blank line.

## 4. `moodle_backup.xml`

`<moodle_backup><information>` contains:
- Version block: `moodle_version`, `moodle_release`, `backup_version`,
  `backup_release`, `backup_date`, `mnet_remoteusers`, `include_files`,
  `include_file_references_to_external_content`.
- Origin block: `original_wwwroot`, `original_site_identifier_hash`,
  `original_course_id`, `original_course_format`, `original_course_fullname`,
  `original_course_shortname`, `original_course_startdate`,
  `original_course_enddate`, `original_course_contextid`,
  `original_system_contextid`.
- `<details><detail backup_id="<32-hex>"><type>course</type>
  <format>moodle2</format><mode>10</mode>…` (mode 10 = MODE_GENERAL).
- `<contents>`: lists every `<activity>` (moduleid, sectionid, modulename,
  title, directory), `<section>` (sectionid, title, directory), and the
  `<course>` (courseid, title, directory).
- `<settings>`: root-level switches (users, activities, files, questionbank, …)
  plus per-section (`section_<id>_included`/`_userinfo`) and per-activity
  (`<mod>_<cmid>_included`/`_userinfo`) settings.

Note the field is `mnet_remoteusers` (not `mnet_remotesite`).

## 5. Course-level files (`course/`)

- **course.xml** — `<course id contextid>` with `shortname`, `fullname`,
  `summary`/`summaryformat`, `format`, visibility/grade/completion flags,
  `startdate`/`enddate`, a `<category id>` block, and `<courseformatoptions>`
  (format-specific; `topics`/`weeks` share a small set, `tiles` has ~9 options
  like `basecolour`, `defaulttileicon`).
- **enrolments.xml** — the three instances every course gets: `manual`
  (status 0, roleid 5), `guest` (status 1), `self` (status 1, roleid 5).
- **inforef.xml** — declares the roles + question categories this course
  references (`<roleref>`, `<question_categoryref>`).
- **roles.xml / filters.xml** — empty container shells.
- **calendar.xml** (`<events>`), **completiondefaults.xml**, **contentbank.xml**
  (`<contents>`) — empty shells.

---

## 6. Section files (`sections/section_<id>/`)

- **section.xml** — `<section id>` with `number` (0-based position), `name`
  (title; `$@NULL@$` for default), `summary`/`summaryformat`, **`sequence`**
  (comma-separated cmids in display order), `visible`, `availabilityjson`
  (empty = `{"op":"&amp;","c":[],"showc":[]}`), `timemodified`.
- **inforef.xml** — usually empty (`<inforef></inforef>`).

---

## 7. The generic activity wrapper

Identical schema for **every** activity type:

- **`<modname>.xml`** — outer wrapper `<activity id="<instance>"
  moduleid="<cmid>" modulename="<mod>" contextid="<modctx>">` containing exactly
  one child `<modname id="<instance>">…</modname>`. The child's content is the
  only type-specific part (see `activity-types.md`).
- **module.xml** — `<module id="<cmid>" version="<plugin-version>">` with
  `modulename, sectionid, sectionnumber, idnumber, added, score, indent,
  visible, visibleoncoursepage, visibleold, groupmode, groupingid, completion,
  completiongradeitemnumber, completionpassgrade, completionview,
  completionexpected, availability, showdescription, downloadcontent, lang,
  tags`. Don't drop `completionpassgrade` or the trailing `lang`.
- **inforef.xml** — `<fileref>`/`<question_categoryref>`/`<grade_itemref>`… as
  needed; empty `<inforef></inforef>` otherwise.
- **roles.xml** — `<roles><role_overrides/><role_assignments/></roles>`.
- **grades.xml** — `<activity_gradebook><grade_items/><grade_letters/></…>`.
- **grade_history.xml** — `<grade_history><grade_grades/></grade_history>`.
- **calendar.xml** — `<events></events>`.
- **filters.xml** — `<filters><filter_actives/><filter_configs/></filters>`.
- **grading.xml** (assign and other advanced-grading modules) —
  `<areas></areas>`.

---

## 8. Top-level stores

- **files.xml** — `<files>` of `<file id>` records (see §9), or `<files></files>`.
- **questions.xml** — `<question_categories>`; Moodle 4.x nests
  `question_category → question_bank_entries → question_bank_entry →
  question_version → question_versions → questions → question`. Each `question`
  has a `qtype` and a `plugin_qtype_<type>_question` block. Empty =
  `<question_categories></question_categories>`.
- **roles.xml** — `<roles_definition>` with the student role
  (`id 5`, `shortname student`, `archetype student`).
- **groups.xml** (`<groups><groupings/></groups>`), **scales.xml**
  (`<scales_definition/>`), **outcomes.xml** (`<outcomes_definition/>`),
  **completion.xml** (`<course_completion/>`) — empty shells unless populated.

## 9. The file store (attachments)

1. A `<file>` record in `files.xml` per file. Field order: `contenthash,
   contextid, component, filearea, itemid, filepath, filename, userid,
   filesize, mimetype, status, timecreated, timemodified, source, author,
   license, sortorder, repositorytype, repositoryid, reference`.
2. Physical content at `files/<contenthash[:2]>/<contenthash>` (single-level
   sharding; filename = bare SHA-1, no extension). `contenthash` = **SHA-1 of
   the file bytes**.
3. Each filearea needs a **directory record**: `filename="."`, `filepath="/"`,
   `filesize=0`, contenthash of the empty file
   `da39a3ee5e6b4b0d3255bfef95601890afd80709` (this record has no physical file).
4. The owning activity's `inforef.xml` links file ids via
   `<fileref><file><id>…</id></file></fileref>`.
- `status=0` = local file present. `component`/`filearea` identify the use
  (`mod_resource/content`, `mod_folder/content`, `mod_page/content`, …).
- Identical bytes dedupe to one physical file (same hash), many `<file>` records.
